# Erp

نرم‌افزار ERP — ماژول اول: هسته مالی (حسابداری)

## پیش‌نیازها
- .NET 10 SDK
- SQL Server 2022 یا 2025 (Developer یا Express) + SSMS
- VS Code با افزونه C# Dev Kit (یا Visual Studio)

## اجرا
- در VS Code: پوشه را باز کنید و **F5** بزنید (پروژه Erp.Api).
- یا در ترمینال: `dotnet run --project src/Host/Erp.Api`
- یا برای تست کامل: `tools\run-test.bat` (نتیجه در `tools\test-log.txt`)

بار اول دیتابیس `ErpCompany_Default` روی `.\ERP` ساخته می‌شود و کدینگ استاندارد (۲۸۴ حساب)،
۱۴ نوع تفصیلی، ارزها، واحدها و تقویم شمسی ۱۳۹۵ تا ۱۴۲۰ بارگذاری می‌شوند.

- رابط کاربری: `http://localhost:5227/` — ورود اول با کاربر **admin** و رمز **admin**؛ بلافاصله رمز جدید خواسته می‌شود.
- صفحه تست API: `http://localhost:5227/scalar` (اول `POST /api/auth/login` با نام کاربری و رمز؛ کوکی ورود برای بقیه درخواست‌ها)

دیتابیس مرکزی `ErpCentral` (کاربران، نقش‌ها، شرکت‌ها) در `appsettings.json` بخش `ConnectionStrings:Central` است و در هر اجرا
ساخته/به‌روز می‌شود. شرکت‌های بخش `Companies` فقط بار اول به کاتالوگ مرکزی اضافه می‌شوند؛ بعد از آن شرکت‌ها از
«مدیریت سیستم ← شرکت‌ها» تعریف می‌شوند.

## ساختار
```
database/                              اسکریپت‌های SQL — مرجع ساختار دیتابیس (README داخلش را بخوانید)
src/
  BuildingBlocks/
    Erp.SharedKernel                   پایه مشترک: Entity، رویداد دامنه، تاریخ شمسی، یکسان‌سازی متن فارسی
    Erp.SharedKernel/Security          IAccessControl (Demand/Has/محدوده داده)، ForbiddenException، تعریف مجوزها
    Erp.Database                       اجراکننده اسکریپت‌های database/migrations و database/central + CompanyConnection
                                       (اتصال و تراکنش مشترک ماژول‌ها) + AuditInterceptor (لاگ تغییرات)
  Modules/Security/                    امنیت (دیتابیس مرکزی، schema sec): کاربران، نقش‌ها، شرکت‌ها، ورود، لاگ امنیتی
    Erp.Security.Domain / Application / Infrastructure
  Modules/BaseData/                    اطلاعات پایه (schema base): اشخاص، نقش‌ها، جدول‌های پایه، بانک‌ها
    Erp.BaseData.Contracts             قرارداد بین ماژول‌ها (PersonKind، RoleCodes، IPersonLinks)
    Erp.BaseData.Domain / Application / Infrastructure
  Modules/Costing/                     بهای تمام‌شده (schema cost): انواع هزینه، عوامل هزینه، انواع و مراکز هزینه
    Erp.Costing.Contracts              قرارداد (CostNature، CostFunction، CostBehavior، ICostDetailLinks)
    Erp.Costing.Domain / Application / Infrastructure
  Modules/Accounting/
    Erp.Accounting.Domain              قواعد حسابداری (کدینگ، تفصیلی شناور، سال/دوره مالی، سند)
    Erp.Accounting.Application         سرویس‌ها و DTOها
    Erp.Accounting.Infrastructure      نگاشت EF Core به جدول‌های fin (و نمای فقط‌خواندنی نقش اشخاص)
  Host/Erp.Api                         میزبان: Web API + رابط کاربری Blazor (Components/)
tests/Erp.Accounting.Tests             تست قواعد دامنه
tools/                                 run-test.bat و تنظیمات اختیاری VS Code
```

**Modular Monolith**: هر ماژول (اشخاص، خزانه، انبار، خرید، فروش، حقوق، بهای تمام شده) یک پوشه زیر
`Modules` با همین سه لایه دارد. زیرسیستم‌ها سند را مستقیم نمی‌نویسند؛ از موتور سند و الگوهای
`fin.PostingTemplates` استفاده می‌کنند و مرجع سند منبع در `SourceModule/SourceDocType/SourceDocumentId` می‌ماند.

## تصمیم‌های هسته مالی (سند «طراحی هسته مالی»)
- کدینگ سه‌سطحی گروه/کل/معین، پایه رایا بیلان (نشریه ۱۶۶ و استاندارد ۱). حساب استاندارد قفل است؛
  شرکت حساب اختصاصی با کد شروع‌شونده از کد والد اضافه می‌کند
- ۶ سطح تفصیلی **شناور**: هر معین برای هر سطح، الزامی بودن و انواع تفصیلی مجاز را تعیین می‌کند؛
  نوعی که گردش دارد از قاعده حذف نمی‌شود
- هر شخص یک تفصیلی مشترک برای همه نقش‌های طرف‌حسابی (اشخاص حقیقی 01001 تا 03999، حقوقی 04001 تا 06999)
  و در صورت نقش کارمند یک تفصیلی کارکنان؛ همه با PersonId به شخص وصل‌اند
- سال مالی با ۱۲ دوره؛ دوره قابل قفل
- سند: پیش‌نویس ← موقت ← دائم (و باطل). شماره موقت از ابتدا، شماره قطعی هنگام دائم شدن، پیوسته
- ارز، نرخ، مقدار، واحد و شماره/تاریخ پیگیری در ردیف سند
- یک دیتابیس برای هر شرکت؛ شرکت با هدر `X-Company` انتخاب می‌شود
- تاریخ میلادی ذخیره می‌شود؛ API تاریخ شمسی (`1405/07/21`) می‌گیرد و برمی‌گرداند
- ي/ك عربی و ارقام فارسی در همه ورودی‌ها و جستجوها یکسان‌سازی می‌شوند

## رابط کاربری
Blazor (Interactive Server) با MudBlazor، راست‌به‌چپ و فونت وزیرمتن (محلی، بدون CDN).
صفحه‌ها سرویس‌های لایه Application را مستقیم صدا می‌زنند؛ هر عملیات در scope جدا اجرا می‌شود
(`Components/Shared/Backend.cs`) تا DbContext در اتصال طولانی کاربر نماند.

## اشخاص و تفصیلی مشترک
- هر شخص **یک تفصیلی مشترک** برای همه نقش‌های طرف‌حسابی دارد (مشتری، تأمین‌کننده، پیمانکار، سهامدار، شرکت وابسته، ...)
  تا مانده کامل او یک‌جا دیده شود. گروه آن «اشخاص حقیقی» یا «اشخاص حقوقی» است.
- نقش‌ها فقط برچسب‌اند؛ کاربر نقش جدید هم می‌تواند تعریف کند (`/base/roles`). نقش **کارمند** تفصیلی جدا در گروه کارکنان دارد.
- در قواعد تفصیلی هر معین «نقش‌های مجاز» تعیین می‌شود؛ فهرست اشخاص در فرم سند به آن‌ها **فیلتر نرم** می‌شود
  (آیکون قیف: نمایش همه اشخاص). ثبت شخص بدون آن نقش ممنوع نیست.
- اطلاعات شخص: هویتی/ثبتی، گروه شخص (درختی)، مالیات و سامانه مودیان، تماس و چند نشانی (نوع، استان، شهر)، افراد رابط،
  حساب‌های بانکی (بانک از جدول بانک‌ها با کد شبا یا پیش‌شماره کارت تشخیص داده می‌شود)، مدارک پیوست (تا ۱۰ مگابایت).
- پیش از ذخیره، اشخاص مشابه (کد ملی، موبایل، شبا یا نام یکسان) هشدار داده می‌شوند.
- اطلاعات کارگزینی (استخدام و ترک کار، حکم، کارگاه، شغل، تحصیلات) در این فرم نیست؛ ماژول کارگزینی فرم‌های خودش را خواهد داشت.
- **جدول‌های پایه** (`/base/lookups`): کشور، استان، شهر (زیر استان)، نوع نشانی، گروه اشخاص، سمت رابط؛ و **بانک‌ها** (`/base/banks`).
  اقلام سیستمی حذف نمی‌شوند؛ قلم استفاده‌شده هم حذف نمی‌شود و فقط غیرفعال می‌شود.
- **حذف امن**: هر حذفی با پرسش تأیید است و فقط وقتی انجام می‌شود که جایی استفاده نشده باشد
  (شخص بدون گردش تفصیلی، تفصیلی بدون ردیف سند، حساب اختصاصی بدون زیرحساب و گردش، سند فقط پیش‌نویس، سال بدون سند).
- کنترل صحت (سرور و فرم، `Erp.SharedKernel.Validation.IranianIds`): کد ملی و شناسه ملی و کارت با رقم کنترل، شبا با mod-97
  (و تشخیص بانک)، موبایل، تلفن، کد پستی، کد اقتصادی، کد فراگیر اتباع، شماره بیمه؛ ارقام فارسی خودکار تبدیل می‌شوند.
- **گروه‌های تفصیلی** (`/detail-types`): تعریف گروه با طول کد و بازه، پیش‌نمایش ظرفیت و کد بعدی، بازه‌های آزاد و الگوی پیشنهادی.
  بازه با حفظ کدهای موجود بزرگ/کوچک می‌شود؛ طول کد و مالک گروهی که تفصیلی دارد ثابت است.
  صفحه هر گروه (`/detail-types/{id}`) تفصیلی‌هایش را نشان می‌دهد؛ تفصیلی‌های غیرشخصی (مرکز هزینه، پروژه، ...) همان‌جا افزوده، تغییر نام، غیرفعال و حذف می‌شوند.

## کدینگ استاندارد
بر پایه کدینگ عملیاتی سپیدار، پاک‌سازی‌شده (اسکریپت ۰۸) و به ترتیب استاندارد ۱ تجدیدنظرشده، از سخت به نقد (اسکریپت ۰۹):
۱ دارایی‌های غیرجاری، ۲ دارایی‌های جاری، ۳ حقوق مالکانه، ۴ بدهی‌های غیرجاری، ۵ بدهی‌های جاری، ۶ درآمدها، ۷ بهای تمام‌شده،
۸ هزینه‌ها، ۹ حساب‌های پایانی و انتظامی. کل‌ها هم به ترتیب صورت‌های مالی‌اند (مثلاً دارایی جاری: 20 پیش‌پرداخت ... 28 موجودی نقد).
کد معین‌ها فاصله دارند (2801 صندوق، 2811 بانک) تا شرکت معین اختصاصی بین‌شان بگذارد.
معین‌های پرکاربرد: 2401 اسناد دریافتنی، 2411 دریافتنی تجاری، 2541 ارزش افزوده دریافتنی، 5001 اسناد پرداختنی، 5011 پرداختنی تجاری،
5111 سایر پرداختنی‌ها، 5125 حقوق پرداختنی، 3001 سرمایه، 6001 فروش.

## ساختار هزینه‌ها و بهای تمام‌شده
- گروه ۸: **کل = گروه (ماهیت)**، **معین = وظیفه**
  - 80 مواد مصرفی: 8001 تولید، 8002 پیمانکاران (بدون تفصیلی؛ بعداً از محاسبه بهای تمام‌شده می‌آید)
  - 81 حقوق و دستمزد، 82 هزینه کارکنان، 83 استهلاک، 84 سایر هزینه‌های عملیاتی: هر کدام
    ..10 مراکز تولیدی، ..40 مراکز خدماتی (پشتیبانی تولید)، ..60 مراکز فروش و توزیع، ..80 مراکز اداری
  - 89 هزینه‌های مالی (تأمین مالی): یک معین، بدون تفکیک وظیفه
- تفصیلی معین‌های هزینه: **سطح ۱ عامل هزینه**، **سطح ۲ مرکز هزینه** (هزینه مالی: سطح ۲ قرارداد تسهیلات، اختیاری).
  عامل فقط در کلِ گروه خودش و مرکز فقط در معینِ وظیفه نوعش ثبت می‌شود (کنترل در فرم سند، سرور و تریگر دیتابیس).
- **عوامل هزینه** (`/costing/factors`): گروه (یکی از پنج کل هزینه) + رفتار (ثابت، متغیر، نیمه‌متغیر با درصد جزء متغیر)؛ ۶۲ عامل پیش‌فرض.
- **انواع مرکز هزینه** (`/costing/center-types`) با وظیفه؛ چهار نوع سیستمی و نوع‌های ریزتر تعریف کاربر.
- **مراکز هزینه** (`/costing/centers`): نوع، بالادست، مسئول؛ برای بهای تمام‌شده: مراکز خدماتی/اداری مبنا و ترتیب تسهیم و
  مراکز گیرنده با سهم (جمع ۱۰۰)، مراکز تولیدی مبنای جذب سربار، فروش بدون تسهیم. مبناها در جدول پایه «مبنای تسهیم و جذب».
- تفصیلی عامل‌ها و مراکز خودکار ساخته می‌شود (مثل اشخاص)؛ عامل/مرکزِ در سند آمده گروه یا وظیفه‌اش عوض و حذف نمی‌شود.

## گروه‌های تفصیلی و قاعده‌های پیش‌فرض
کد تفصیلی در کل سیستم یکتاست تا در ورود سند، گزارش و ایمپورت، کد به‌تنهایی کافی باشد. گروه‌های پیش‌فرض ۶ رقمی با پیشوند گروه‌اند:
صندوق 100001، تنخواه 101001، بانک 110001، اعتبار اسنادی 120001، تسهیلات 130001، ماه سررسید 150001–150012 (فروردین تا اسفند، بدون سال)،
کارکنان 300001، مراکز هزینه 400001، عوامل هزینه 410001، پروژه 500001، اشخاص حقیقی 600001–799999، اشخاص حقوقی 800001–999999.
گروه‌های «انبارها» و «دارایی‌های ثابت» غیرفعال‌اند (زیرسیستم انبار و دارایی ثابت جزئیات را نگه می‌دارند).

قاعده‌های پیش‌فرض (از صفحه کدینگ قابل تغییرند):
- **همه سطح‌ها اجباری‌اند**؛ یک معین با تعداد سطح متفاوت در ردیف‌های مختلف ثبت نمی‌شود.
- اسناد پرداختنی (کوتاه و بلندمدت) به تفکیک ماه سررسید؛ اسناد دریافتنی به تفکیک صندوق؛ اسناد در جریان وصول به تفکیک حساب بانکی.
- دارایی ثابت، استهلاک انباشته و موجودی‌ها بدون تفصیلی؛ سپرده ضمانت‌نامه و ضمانت‌نامه‌های انتظامی فقط با بانک.
- دریافتنی و پرداختنی‌ها با اشخاص (فیلتر نقش مشتری/تأمین‌کننده)، کارکنان، تسهیلات، اعتبار اسنادی برای سفارشات خارجی.

## موتور صدور سند خودکار
- هر فرمی که سند دارد (فعلاً «شناسایی هزینه») یک **الگو** دارد (`/posting-templates`): ردیف‌ها با کلید، طرف بدهکار/بستانکار و
  معین ثابت، یا قاعده (`cost`: کل از گروه عامل هزینه، معین از وظیفه مرکز هزینه). کاربر معین ردیف‌های ثابت را عوض می‌کند.
- تفصیلی‌ها خودکار: فرم «شخص، عامل، مرکز یا تفصیلی» می‌دهد و هر سطح قاعده معین با اولین مورد مناسب پر می‌شود.
- زیرسیستم‌ها فقط از `IVoucherPosting` (در `Erp.Accounting.Contracts`) استفاده می‌کنند؛ فرم و سندش در یک تراکنش:
  ثبت فرم ← سند موقت، اصلاح فرم ← بازنویسی همان سند (همان شماره)، حذف فرم ← حذف سند. سند دائم‌شده فرم را قفل می‌کند.
- سند خودکار از فرم سند اصلاح، برگشت به پیش‌نویس، باطل یا حذف نمی‌شود (فقط دائم کردن)؛ لینک «باز کردن فرم» دارد.
- هر سند منبع حداکثر یک سند زنده دارد (`UX_Vouchers_LiveSource`).

## شناسایی هزینه
فاکتور خدماتی تأمین‌کننده (`/expenses`، ماژول `src/Modules/Expenses`، schema `exp`): تأمین‌کننده، شماره و تاریخ فاکتور فروشنده،
طرف بستانکار (پرداختنی تجاری پیش‌فرض یا سایر)، مالیات و عوارض ارزش افزوده در سربرگ؛ ردیف‌ها عامل + مرکز هزینه + مبلغ
(هزینه مالی مرکز نمی‌خواهد). سند: بدهکار معین هزینه هر ردیف و ارزش افزوده دریافتنی، بستانکار طرف حساب به جمع کل.
فاکتور تکراری یک تأمین‌کننده (همان شماره) پذیرفته نمی‌شود. پرداخت بعداً در خزانه‌داری.

## خزانه‌داری
ماژول `src/Modules/Treasury` (schema `trs`)، همه فرم‌ها با سند خودکار روی موتور صدور سند و فهرست کنار فرم:
- **تعاریف** (`/treasury/setup`): صندوق، حساب بانکی (بانک، شعبه، شماره، شبا، نوع)، تنخواه‌گردان (دارنده) و انواع دریافت/پرداخت
  (هر نوع معین طرف حساب را تعیین می‌کند، مثلاً «دریافت از مشتری» ← 2411). تفصیلی صندوق/بانک/تنخواه فقط از همین‌جا ساخته می‌شود
  (`ITreasuryDetailLinks`) و در «گروه‌ها و حساب‌های تفصیلی» دستی ساخته نمی‌شود.
- **دریافت / پرداخت**: یک طرف حساب، یک نوع و چند ردیف با ابزار نقد، بانکی، چک (و در پرداخت «خرج چک دریافتی»).
  چک دریافتی و صادره با سریال، شناسه صیاد و سررسید همین‌جا ثبت می‌شود. فرمی که چکش عملیات خورده قفل است.
- **انتقال وجه**: بین صندوق، بانک و تنخواه (شارژ تنخواه)، با کارمزد اختیاری (عامل + مرکز هزینه).
- **صورت‌هزینه تنخواه**: هر ردیف یا «هزینه» (عامل + مرکز، با ارزش افزوده) یا «پرداخت به طرف حساب» (نوع پرداخت + شخص،
  مثل پرداخت بدهی یا مساعده)؛ بستانکار تنخواه‌گردان به جمع کل.
- **دسته‌چک، سفته و ضمانت‌نامه** (`/treasury/instruments`): اسناد پرداختنی از قبل تعریف می‌شوند. دسته‌چک (حساب بانکی + بازه سریال)
  و دفتر سفته (سری، بازه، سقف مبلغ) با برگ‌هایشان (سفید/استفاده‌شده/باطل)؛ ضمانت‌نامه بانکی (نزد ما/نزد ذی‌نفع/باطل).
  چک صادره فقط از برگ سفید دسته‌چک همان حساب؛ چک و سفته تضمینی پرداختی از برگ دفترچه‌ها؛ ضمانت‌نامه پرداختی از ضمانت‌نامه تعریف‌شده.
  حذف یا اصلاح فرم برگ را آزاد می‌کند؛ استرداد ضمانت‌نامه را دوباره «نزد ما» می‌کند.
- **عملیات اسناد دریافتنی**: واگذاری به بانک، وصول (از بانک واگذاری یا مستقیم به صندوق/بانک)، برگشت، حقوقی، عودت، برگشت از واگذاری.
  **پرداختنی**: پاس و ابطال. هر عملیات چند چک و یک سند؛ برگرداندن = حذف آخرین عملیات چک.
- **اسناد تضمینی**: دریافتی/پرداختی (چک، سفته، ضمانت‌نامه، سایر) با سند انتظامی ثبت و سند معکوس استرداد.
- **گزارش‌ها**: چک‌های دریافتنی/پرداختنی با فیلتر و سابقه هر چک، سررسید ماهانه (نقدینگی)، موجودی صندوق/بانک/تنخواه تا تاریخ.

## شماره فرم‌ها و ارزش افزوده
- هر نوع فرم شماره سیستمی خودش را از 000001 دارد (جدا از شماره فاکتور فروشنده)؛ عملیات چک برای دریافتنی و پرداختنی جدا.
- نرخ مالیات و عوارض ارزش افزوده سال به سال در `/base/vat-rates` (اطلاعات پایه) تعریف می‌شود. ارزش افزوده **در هر ردیف** است
  (کلید مشمول/معاف ردیف؛ یک فرم می‌تواند ردیف مشمول و معاف با هم داشته باشد) و از نرخ سالِ تاریخ فرم خودکار حساب می‌شود
  (قابل اصلاح دستی). جمع آن در همان سند فرم به معین ارزش افزوده می‌رود.

## ورود، کاربران و سطوح دسترسی
- **ورود** با کوکی (HttpOnly). صفحه‌های `/account/login`، `/account/change-password` و `/account/company` بدون اتصال تعاملی‌اند.
  کاربری که چند شرکت دارد بعد از ورود شرکت را انتخاب می‌کند؛ «تغییر شرکت» از منوی کاربر بالای صفحه.
- **رمز**: فقط هش یک‌طرفه PBKDF2-SHA512 با salt جدا ذخیره می‌شود؛ قابل استخراج نیست و فقط بازنشانی می‌شود.
  حداقل طول، حرف و رقم، بدون نام کاربری. ارقام فارسی و لاتین رمز یکی حساب می‌شوند.
- **قفل حساب** بعد از چند ورود ناموفق پشت سر هم (تنظیمات امنیتی)؛ مدیر قفل را باز می‌کند. پیام ورود برای کاربر ناموجود و رمز
  نادرست یکی است. **خروج خودکار** بعد از بی‌کاری (پیش‌فرض ۳۰ دقیقه). تغییر رمز، غیرفعال شدن یا «خروج از همه نشست‌ها» نشست‌های
  باز کاربر را باطل می‌کند (`SecurityStamp`).
- **نقش** = مجموعه مجوز (سراسری). برای هر شرکت یک یا چند نقش به کاربر داده می‌شود؛ مجوز او اجتماع نقش‌های فعالش است.
  مدیر سیستم همه مجوزها و همه شرکت‌ها را دارد و فقط مدیر سیستم می‌تواند مدیر سیستم تعیین کند.
- **مجوزها** در کد هر ماژول تعریف شده‌اند (`AccountingPermissions`، `TreasuryPermissions`، ...): برای هر فرم مشاهده/ایجاد/اصلاح/حذف
  و کارهای خاص (موقت/دائم/برگشت/ابطال سند، هر عملیات چک، استرداد سند تضمینی، ابطال برگ، باز و بسته کردن دوره، ...).
  کنترل اصلی در سرویس‌هاست (`access.Demand(...)`)؛ منو، جستجوی سراسری و دکمه‌های فرم (`FormToolbar Permission=...`) هم مطابق مجوز
  پنهان می‌شوند و باز کردن مستقیم آدرس صفحه بدون مجوز «دسترسی ندارید» نشان می‌دهد. جستجوی اشخاص، حساب‌ها و جدول‌های پایه برای
  استفاده در فرم‌های دیگر آزاد است.
- **محدوده داده** برای هر کاربر و شرکت: صندوق‌ها، حساب‌های بانکی، تنخواه‌گردان‌ها و سال‌های مالی مجاز (یا همه)، و
  «فقط فرم‌ها و اسنادی که خودش ثبت کرده». فرم‌ها، فهرست‌ها و گزارش‌ها همین محدوده را رعایت می‌کنند.
- **لاگ تغییرات** (`audit.ChangeLog` در دیتابیس شرکت): هر ایجاد/اصلاح/حذف با کاربر، IP، زمان، مقدار قبلی و جدید (فقط فیلدهای
  تغییرکرده)؛ ردیف‌ها به فرم اصلی وصل‌اند. دکمه **تاریخچه** روی فرم‌ها و گزارش «لاگ تغییرات» در مدیریت سیستم.
  بازنویسی ردیف‌های بدون تغییر (حذف و درج دوباره هنگام اصلاح فرم) در نمایش حذف می‌شود.
- بعد از ۲۰ ورود ناموفق در ۵ دقیقه از یک نشانی IP، تلاش‌های بعدی آن IP تا پایان بازه رد می‌شود.
  دو دقیقه مانده به خروج خودکار، هشدار روی صفحه می‌آید و با یک کلیک زمان از نو شمرده می‌شود.
- «مشاهده» لازمه هر کار دیگر روی همان فرم است و در ذخیره نقش خودکار اضافه می‌شود. تاریخچه فقط برای فرمی که کاربر اجازه
  دیدنش را دارد (با رعایت محدوده داده) نمایش داده می‌شود.
- **لاگ امنیتی** (دیتابیس مرکزی): ورود/خروج، ورود ناموفق، قفل، تغییر/بازنشانی رمز، تغییر کاربران و نقش‌ها و شرکت‌ها، تلاش بدون مجوز.
- **خطای فنی**: در فایل روزانه `src/Host/Erp.Api/logs/erp-تاریخ.log` با کد پیگیری (مثل `E-3F9A2C1B`) که به کاربر هم نشان داده می‌شود.
- صفحه‌های «مدیریت سیستم»: کاربران، نقش‌ها و مجوزها (درخت مجوز با کپی نقش)، شرکت‌ها (ساخت/به‌روزرسانی دیتابیس)، لاگ تغییرات،
  لاگ امنیتی، تنظیمات امنیتی.

## رفتار فرم‌ها
- نوار ابزار بالای هر فرم: جدید، اصلاح، حذف، ذخیره، انصراف، مشاهده سند (+ دکمه‌های خاص فرم مثل استرداد یا موقت/دائم کردن سند).
- رکورد موجود (از فهرست کنار فرم یا فهرست اصلی) در **حالت نمایش** باز می‌شود؛ با «اصلاح» ویرایش و با «ذخیره» یا «انصراف» تمام می‌شود.
  رفتن به رکورد دیگر وسط ویرایش تأیید می‌خواهد.
- میانبرها: **Ctrl+S** ذخیره، **F2** اصلاح، **Esc** انصراف، **Alt+N** جدید (هر چیدمان صفحه‌کلید)؛ **Ctrl+K** جستجوی سراسری.
- جمع فرم‌ها به حروف نمایش داده می‌شود. فهرست کنار فرم با » بسته و باز می‌شود.
- دکمه «تاریخچه» تغییرات فرم (با ردیف‌هایش) را به ترتیب زمان نشان می‌دهد: چه کسی، کی، از چه مقداری به چه مقداری.

## صفحه نخست
تب ثابت اول (بسته نمی‌شود): دسترسی سریع، کارهای مانده (سند پیش‌نویس و موقت)، کارت‌های سال مالی جاری (نقد و بانک، دریافتنی تجاری،
پرداختنی‌ها، درآمد و هزینه ماه) و آخرین سندها. جستجوی سراسری بالای صفحه با **Ctrl+K**: فرم‌ها، معین‌ها (← دفتر معین) و اشخاص.

## تب‌ها
هر فرمی که باز می‌شود یک تب است و با جابه‌جایی بین تب‌ها وضعیتش (فرم نیمه‌کاره، فیلترها) می‌ماند. باز کردن دوباره همان فرم تبش را جلو می‌آورد؛
کلیک وسط ماوس یا × تب را می‌بندد و «بستن بقیه» همه را جز تب فعلی. حداکثر ۱۵ تب باز می‌ماند.

## گزارش‌ها
- **تراز آزمایشی** (`/reports/trial-balance`): سطح گروه، کل، معین و تفصیلی؛ نمایش ۴ یا ۶ ستونی؛
  فیلتر بازه تاریخ، بازه شماره قطعی سند، موقت/دائم و حذف اسناد بستن و اختتامیه.
  با کلیک روی گروه ← کل‌ها، روی کل ← معین‌ها، روی معین ← دفتر. دکمه کنار معین ← تراز تفصیلی همان معین.
  در تراز ۶ ستونی، سند افتتاحیه همیشه جزو «مانده ابتدای دوره» است.
- **دفتر معین و تفصیلی** (`/reports/ledger`): مانده ابتدای بازه، ردیف‌ها با مانده جاری و تشخیص بد/بس؛ کلیک روی ردیف ← سند.
- **مرور حساب‌ها** (`/reports/review`): گردش و مانده به تفکیک هر سطح (گروه، کل، معین، تفصیلی سطح ۱ تا ۶، همه تفصیلی‌ها، اسناد)
  با مسیر انباشته (یک حساب و چند تفصیلی). کلیک روی ردیف یک سطح پایین می‌رود؛ «نمایش به تفکیک» همان مسیر را به سطح دیگری
  نشان می‌دهد (مثلاً یک تفصیلی به تفکیک معین‌هایش). در سطح «اسناد» مانده جاری هر سند. دفتر هم چند تفصیلی را با هم می‌پذیرد.
- **ترازنامه و سود و زیان** (`/reports/statements`): در سطح کل از روی گروه‌های کدینگ استاندارد. ترازنامه در «تا تاریخ» در مقایسه
  با ابتدای بازه؛ سود و زیان بسته‌نشده سطر جدای حقوق مالکانه است. سود و زیان: درآمد عملیاتی، بهای تمام‌شده (گروه ۷)، ناخالص،
  هزینه‌های عملیاتی (گروه ۸ جز ۸۹)، سایر عملیاتی (۶۴)، عملیاتی، مالی (۸۹)، غیرعملیاتی (۶۵ و بقیه ۶)، خالص؛ مقایسه با سال قبل.
  اسناد بستن و اختتامیه در صورت‌ها حساب نمی‌شوند.
- **دفاتر قانونی** (`/reports/books`): روزنامه (هر سند به تفکیک کل، اول بدهکارها) و کل (هر کل جدا با نقل از قبل و مانده)؛ فقط اسناد
  دائم و به ترتیب شماره قطعی.
- **خروجی اکسل** همه گزارش‌ها و فهرست‌ها (ClosedXML، راست‌به‌چپ، مبالغ عدد واقعی و کدها متن) با مجوز `sys.export.excel`؛ هر خروجی
  در لاگ امنیتی ثبت می‌شود. چاپ سند تکی و گروهی (`/vouchers/print`، هر سند یک صفحه A4، پیش‌نویس با علامت) با مجوز `acc.voucher.print`.
- API: `POST /api/accounting/reports/trial-balance`، `ledger`، `review`، `balance-sheet`، `income-statement`، `journal`، `general-ledger`.
- پیش‌نویس و باطل هیچ‌وقت در گزارش نمی‌آیند.

## افتتاحیه، بستن سال و ترتیب اسناد
- هر سال فقط یک سند افتتاحیه غیرباطل (ایندکس یکتا، اسکریپت ۱۴) با تاریخ روز اول سال؛ سند بستن و اختتامیه دستی ساخته نمی‌شود.
- **ورود سند از اکسل** (`/vouchers/import`): فایل نمونه با برگه راهنمای معین‌ها و قواعد تفصیلی؛ همه ردیف‌ها با `VoucherService.CheckAsync`
  پیش از ثبت بررسی می‌شوند (همه خطاها، نه فقط اولی) و سند پیش‌نویس ثبت می‌شود. **ورود اشخاص از اکسل** (`/persons/import`): همه یا هیچ.
- **دریافت/پرداخت اول دوره** (`IsOpening`): فقط ردیف چک، بدون سند (مانده در افتتاحیه است)؛ عملیات بعدی چک سند عادی می‌خورد.
- **بستن سال** (`/fiscal-years/closing`، `ClosingService`): صدور اسناد (موقت) بستن حساب‌های موقت (سود و زیانی ← 3801 سود و زیان جاری)،
  اختتامیه (همه حساب‌های دائم و انتظامی، با همان ترکیب تفصیلی) و افتتاحیه سال بعد (3801 ← 3701 انباشته؛ سال بعد اگر نباشد ساخته می‌شود)
  و قفل سال؛ «برگشت» تا وقتی هیچ‌کدام دائم نشده؛ «قطعی کردن» = دائم شدن بستن و اختتامیه و بستن همیشگی سال. پیش‌شرط: هیچ سند
  پیش‌نویس یا موقت در سال نباشد و سال بعد افتتاحیه دستی نداشته باشد. ردیف‌های انتقال مانده (`Voucher.AddCarryLine`) قواعد امروزِ
  تفصیلی را دوباره بررسی نمی‌کنند.
- **ترتیب و دائم کردن اسناد** (`/vouchers/numbering`): دائم کردن گروهی تا تاریخ به ترتیب تاریخ، و شماره‌گذاری مجدد اسناد دائم سال باز
  به ترتیب (افتتاحیه، تاریخ، عادی، بستن، اختتامیه). تریگر `trg_Vouchers_Protect` (اسکریپت ۱۵) روی سند دائم فقط تغییر `VoucherNo` را می‌پذیرد.

## تست‌ها
`dotnet test` تست‌های دامنه را اجرا می‌کند. تست‌های گزارش روی SQL Server واقعی‌اند و فقط وقتی اجرا می‌شوند که
متغیر `ERP_TEST_SQL` تنظیم شده باشد؛ `tools\run-test.bat` آن را روی دیتابیس جداگانه `ErpCompany_Test` تنظیم می‌کند
(هر بار از صفر ساخته می‌شود و به دیتابیس اصلی کاری ندارد). تست‌های امنیت روی `ErpCentral_Test` کنار آن اجرا می‌شوند.
بخش API در `run-test.bat` با کاربر `ERP_USER` و رمز `ERP_PASS` (متغیر محیطی) وارد می‌شود؛ پیش‌فرض admin/admin فقط تا قبل از
اولین تغییر رمز کار می‌کند.

## کالا، خرید و فروش
- **کالا و خدمات** (`/inventory/items`) و **گروه‌های کالا** (`/inventory/groups`): گروه معین فروش، برگشت از فروش و خرید (موجودی) را تعیین می‌کند؛
  کالا کد (خالی = خودکار ۶ رقمی)، نوع از گروه، واحد، شناسه کالا/خدمت مودیان (۱۳ رقم)، معاف/مشمول ارزش افزوده و قیمت فروش دارد.
  گروه‌های پیش‌فرض: کالای بازرگانی (6003/6202/2206)، محصولات (6001/6201/2203)، مواد و قطعات (6002/6002/2201)، خدمات (6101).
- **فاکتور خرید** (`/purchases`): فقط کالا؛ بدهکار موجودی گروه کالا (پس از تخفیف) و 2541، بستانکار تأمین‌کننده. خرید خدمت با شناسایی هزینه.
- **فاکتور فروش** (`/sales`): بدهکار 2411 مشتری و 6301 تخفیف، بستانکار معین فروش گروه (ناخالص) و 5141. نوع صورتحساب و روش تسویه برای مودیان؛
  پروژه اختیاری برای درآمد خدمات (6101 تفصیلی پروژه می‌خواهد). دریافت وجه از خزانه‌داری.
- **برگشت از خرید و فروش** (`/purchases/returns`، `/sales/returns`): همیشه از یک فاکتور؛ مقدار هر ردیف حداکثر مانده آن (کنترل در سرویس و تریگر)،
  مبلغ، تخفیف و ارزش افزوده به نسبت مقدار و آخرین برگشت باقی مبلغ را می‌گیرد. فاکتوری که برگشت دارد اصلاح و حذف نمی‌شود.
- مبالغ به ریال گرد می‌شوند. بهای تمام‌شده کالای فروش‌رفته تا آمدن انبار خودکار ثبت نمی‌شود (روش ادواری پایان دوره).
